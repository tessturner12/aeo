## Cost blowup caught, cadence and cohort design corrected

Asked to just run the built rig ("okay lets go"). Before spending real money, sanity-checked the appendix's own claimed runtime/budget against what the actual code would do — and it didn't hold up.

- **Nightly cron would have cost ~$1,000+/month against a stated £20-35 budget.** The appendix's crontab ran the full 540-call cycle every night for 30 nights; nobody had multiplied real per-call cost by 30. Measured real usage (not estimated) on live test calls: Claude web search runs ~20k input tokens/call (search results dominate the token count, not the answer), OpenAI ~38k. Real cost ~$0.08-0.10/call on both, ~$35-40 for one full cycle alone.
- **Two applied fixes, both verified empirically, not assumed:**
  - Claude: `max_uses=1` on the web search tool. Measured before/after — input tokens dropped from ~20.7k to ~9.1k average across 3 test calls, searches from 2 to ~0.7. Real cost dropped to ~$0.035-0.05/call.
  - OpenAI: `search_context_size="low"` on the Responses API's `web_search` tool (not the `gpt-4o-search-preview`/`chat.completions.create` path — that's the dead surface already replaced). Tested for real: **it did not reliably cut tokens** the way Claude's fix did — one call came back higher than baseline, two others much lower. Kept it anyway (real, documented cost lever, per OpenAI's own docs "does not guarantee" a token count) but reported it honestly rather than claiming a clean win.
- **Weighted run counts by cluster size.** `fixed_fee_positioning` and `general_recommendation` (the only two clusters big enough to support a real CI) get N=5 on baseline/after; everything else defaults to N=3 — was previously flat N=5 everywhere, spending real budget on cells (`tax_efficiency` at 2 questions) that could never produce a trustworthy interval regardless of N.
- **Replaced nightly cron with 3 deliberate checkpoints** (`baseline`, `canary`, `after`) — added a `checkpoint` column to `runs` (schema.sql), a `MODE` argv flag to `rig.py`, and removed the recurring crontab entry from Appendix A.
- **Canary checkpoint, tiered rather than a bare smoke test.** Covers all three tiers (test + near-control at N=3, far-control at N=2, ~285 calls) instead of just the test cluster at N=1 — gives a real trend point and lets spillover show up before the after-checkpoint budget is spent. Confirmed via `estimate_cost.py`: ~$12.35, under the $15 target.
- **Cohort design: dropped the holdout tier.** Appendix J's original script randomised at the topic level and popped one cluster into permanent holdout — never actually guaranteed `fixed_fee_positioning` landing in test (the point of the whole design), and cost real N on an already-thin dataset. Replaced with a deterministic split (`fixed_fee_positioning` → test, everything else → control) plus a near/far tiering of control by semantic distance from the intervention (`general_recommendation`, `switching_accountants` = near; the other 4 = far) — same drift-detection purpose as holdout, more precisely, via the near/far breakdown and a direct cited-URL spillover check (Appendix M) instead of inferring it from a number.
- **Reclassified `q001`** ("cheapest monthly online accountants uk") from `general_recommendation` into `fixed_fee_positioning` — it's a pricing-framing question, not a generic-recommendation one. `fixed_fee_positioning` is now 10 questions (was 9), `general_recommendation` 8 (was 9). Logged in the row's own `notes` field, not silently changed.
- **Added framing sub-tags** (`framing:fixed_fee` / `framing:monthly` / `framing:annual`) to the 10 `fixed_fee_positioning` questions — turns out this distinction was already deliberately baked into Day 2's question research (q065-q068's notes already said "added post-Day 1 to test monthly/annual-plan terminology vs 'fixed fee' phrasing") before this session's framing-tag work made it queryable. Sharpens the actual hypothesis: Mighty's hero copy already says "£60pm" (monthly-framed) but not "fixed fee" — predict monthly-framed questions score higher at baseline and move less after the intervention than fixed-fee/annual-framed ones.

The original £15-per-provider cap (Appendix B) was set before any of these numbers existed — flagged to raise both to £25-30 before the after-checkpoint runs, so a cap doesn't fail mid-run at the worst possible time.

## Cross-checked the power analysis against a second model's independent read — two real gaps found, both fixed

A companion Claude chat reviewed the power-analysis work above and raised three points. Verified each numerically rather than just agreeing:

My original scenario table topped out at 15% baseline as the "realistic" upper bound — the actual data support real uncertainty roughly double that. Strengthens (doesn't weaken) the baseline-gate recommendation.
- **"Is n=50 pooled or per-surface — it matters given Day 1's cross-platform heterogeneity" — real gap, confirmed by grep.** Checked every query I'd added to Appendices K and M: all of them pooled across Perplexity/Claude/OpenAI, none broke out by surface — unlike Appendix I's pre-existing descriptive query, which does.
